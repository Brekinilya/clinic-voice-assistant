## A. Назначение и целевой результат

DBI, кейс телефонной регистратуры: пациент записывается к врачу, узнаёт/отменяет/переносит свои записи, получает организационную справку; сложный случай передаётся сотруднику. Система также напоминает о визите. Требуемый результат — проверяемое действие/честный отказ или ручной маршрут, без диагноза, выдуманного слота, согласия или успешной записи при неизвестном исходе.

Есть текстовый браузерный чат, браузерный голос и SIP. Текст — рабочий резерв при проблемах звука, а не отдельный обход доменных правил. `offline_test` использует явно обозначенный эмулятор, `hackathon` — выданную МИС с тестовыми данными; `clinic_pilot` запрещён валидатором. Допуск к реальным медицинским данным не подтверждён.

## B. Архитектура и контракты

Общая цепочка: **SIP-шлюз → Asterisk/ARI → RTP → CallSession → VAD/локальный ASR → safety + RulesNlu → детерминированный диалог → доменные сервисы → МИС → проверенный результат → TTS**. Браузерный WebSocket использует тот же CallSession. Safety умеет прервать обработку ещё на partial, не дожидаясь МИС.

Сохранять интерфейсы и семантику:

- `RulesNlu(doctor_names).parse(NluRequest) -> NluResult`, сообщения `app/contracts.py`; intent/slots/evidence извлекают данные, не выполняют действие.
- `DialogueService.handle(call_id, Turn)`, `partial(...is_final=False)`, `input_started(call_id, turn_id)`, `end(call_id)`; обычные HTTP final строго упорядочены. `input_started` может пропускать отменённые голосовые фразы — **не использовать это как разрешение любых пропусков HTTP**.
- `Approval` привязан к действию/ревизии/turn/version/input_epoch. Новая речь отзывает ещё не отправленное действие; отправленный HTTP требует журнала и сверки.
- `TransferResult(attempt_id, call_id, route, priority, outcome, reason)`: `connected/no_answer/failed/aborted`, техническая причина без ПДн. Запрошенный перевод не означает соединение. Обычная заявка МИС — по фактическому connected; P1 имеет отдельное оговорённое техническое исключение с настроенным technical_client_id, без поиска пациента на срочном пути.
- T11: `open_outbound(call_id, OutboundContext)`, `outbound_event(call_id, OutboundEvent)`. Открытие — turn1, первая речь — turn2; `fence`/попытка проверяются перед действием. Первый ответ «да» подтверждает адресата, не изменение визита. `ReminderResult.mis_status` различает applied/pending/manual; неизвестный PATCH только читаем.
- МИС: `POST /api/v1/escalations` имеет только `client_id` и `description`≤1000. Серверной идемпотентности нет; после неизвестного POST нельзя повторять его по отсутствию результата GET. Маркер/описание/клиент должны совпасть точно, неоднозначность → manual.

## E. Принятые решения и уже исправленные ошибки

- Сохраняем Python3.11/FastAPI/httpx/Pydantic/SQLAlchemy/asyncpg, PostgreSQL, SQLite, Asterisk и локальные ASR/TTS. Не вводим новую FSM, LLM-интенты, нечёткую автоматическую идентификацию или переобучение вместо исправления логики.
- Разделены extraction → deterministic validation → execution. Явный год даты сохраняется; исключённые дни проходят end-to-end; время не извлекается из DOB. Регистр и ё→е нормализуются, редкое похожее ФИО само по себе не разрешает выбрать пациента. `profile_key` общий для NLU/расписания/МИС.
- Активный вопрос определяет смысл короткого «да/нет/повторите». Смена цели/пациента/параметров отзывает прежнее предложение; после отправки HTTP — журнал и сверка. D00 и часть D01/V01 уже включены; это уточнения диалога в исходном T-backlog, не замена нумерации T03.
- Единый бюджет МИС PostgreSQL по хешу токена: внутренний8/мин, внешний по контракту10/мин. Не поднимать внутренний лимит и не создавать отдельные бюджеты процесса. 429/Retry-After закрывает доступ всем; приоритеты и ограниченное ожидание уже существуют. Имена для NLU локальные, не GETdoctors на каждое «да».
- Время клиники **GMT+4**, не timezone Windows/Москва. Регистратура по кейсу: будни07–20, суббота08:30–15, воскресенье закрыто; окно напоминаний T11 — другой календарь. Не продлевать вручную свежесть старого индекса и не отключать правило24часов ради демонстрации.
- T11 бережёт чужой комментарий пациента; неизвестный PATCH не повторяется. Исходящий контакт берётся локально; дозволены только собственные SIP-направления шлюза. Автодозвон callback на произвольный номер/SMS не реализованы.
- Реальные пароли, API-токены, аудио людей/ПДн не публиковать. Командный BasicAuth/Origin есть; owner в операторском API — demo-ID, **не полноценный RBAC**. LLM-доступ организаторов не доказывает разрешения отправлять туда ПДн.

Уже исправлено в R01/4551c6f: старые гонки input_started/insert и истёкшего lease; суббота/ноябрьский праздник; повтор finish; бесконечное непонимание callback из-за сброса invalid_turns; двойной input_started; непотреблённый turn после repeat; отзыв согласия partial; ложный failed вместо реального connected после timeout журнала. Сохранять тесты, не возвращать эти ошибки. Полное поведение календаря2026 и final-text гонка ещё не доказаны/не исправлены.

## I. Первая задача Luna: A03-R02 / R02-1 — отзыв согласия новым final

**Цель:** новая итоговая фраза пациента, полученная до атомарной фиксации callback, запрещает вставку по старому «да». Одновременно обычный HTTP сохраняет строгий порядок и повтор команд не создаёт дублей. Это первый шаг уже существующего A03-R02, не самостоятельная новая архитектура.

**Уже есть:** draft CAS/version/input_epoch, идемпотентный input_started с started_turn_id, защита нового partial, operator lease, журнал задачи; функции `callback_turn`, `callback_input_started`, `create_callback_task`. PostgreSQL и memory должны иметь одинаковый контракт.

**Причина/граница:** в HANDOFF `DialogueService._handle` отзывает согласие по partial, а итоговый callback обходит обычные claim/complete. Порядок обработанного turn и наблюдение новой речи недостаточно разделены. Не лечить вызовом callback_input_started перед любым final: он устанавливает last_turn_id=turn-1 и легализует произвольный пропуск HTTP. Не задавать desired architecture заранее: выбрать минимальное расширение существующих хранилищ/квитанций с доказанными инвариантами.

**Воспроизведение без МИС/телефона:**

1. `prepared_callback()` из tests/test_handoffs_r01.py доводит черновик до confirm после ходов2/3/4 (да, вымышленный контакт, ближайшее время).
2. DialogueState того же call_id — HANDOFF, реальный DialogueService+RulesSafety+HandoffService.
3. Задержать `store.create_callback_task` через asyncio.Event; запустить `dialogue.handle(turn5, «да»)` до входа во вставку.
4. Пока вставка ждёт, вызвать `dialogue.handle(turn6, новый вымышленный номер)` без отдельного input_started, затем отпустить задержку.
5. Сейчас задача сохраняется по старому номеру/согласию. Ожидание: **задачи по старому согласию нет**; состояние/ответ позволяют явное новое подтверждение, не зависают. Готовый тест — `test_new_final_text_revokes_pending_confirmation_without_skipping_turn` в review-fixture.

**Действия:**
