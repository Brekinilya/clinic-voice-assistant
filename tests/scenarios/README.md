# План тестов: сценарии разговора

Регламент (раздел 10) требует перед вводом сценария и после каждого изменения прогонять контрольные диалоги, включая все ветвления и красные флаги. Здесь они записаны как данные: 16 контрольных диалогов приложения Д, эталонные диалоги раздела 5 и отдельные правила перевода.

## Уровни проверки

| Уровень | Что проверяем | Где | Когда |
|---|---|---|---|
| Модульные | Словари, разборщики, `safety.check`, длина и ссылки реплик | `tests/nlu`, `tests/policies`, `tests/voice` | есть, на каждом коммите |
| Реплики пациента в сценариях | Флаги и правило перевода на каждой реплике, локальный разбор ответов, интент по правилам | `test_scenarios.py` | есть |
| Сценарий целиком через текстовый канал | Состояния, варианты, запрет раскрытия, итоговые записи, количество запросов и изменений | `test_scenarios.py::test_dialog_end_to_end`, выполняется через настоящее приложение | на каждом коммите; известные пробелы — явные `xfail` |
| Голос | Те же сценарии: синтез реплик пациента → распознавание → диалог → синтез; точность ФИО, дат, времени | `tests/voice` | 16–22.10 |
| Настоящий стенд | Выборочно те же сценарии, только вымышленные данные, лимит 10 запросов в минуту | ручной прогон | перед заморозкой 22.10 |
| Задержка | Простой ответ ≤ 1,5 с, с разбором ≤ 2,5 с (p95); фраза-заполнитель, если стенд думает дольше 1,5 с | замеры по сценариям | 20–22.10 |

## Критерии прохождения

С 17.10 безусловный skip полного диалога удалён. Все 56 исходных вариантов
и дополнительная регрессия общей квоты исполняются в изолированных ресурсах.
Приёмку определяет `python -m tests.scenarios.run`, который возвращает ненулевой
код при fail/unsupported. Обычный pytest проверяет также отсутствие новых
регрессий относительно `known_issues.json`; его `xfail` не означает готовность кейса.

Известное исключение разрешено только при полном совпадении списка доказательств.
Новая ошибка, исправление старой, нарушение безопасности или ошибка runner
требуют разбора и не скрываются этим списком. Автоматически перезаписывать его
из нового отчёта нельзя. После реализации функции сначала подключается проверка
реального результата, затем удаляется соответствующее исключение.

`GAPS` в `runner.py` перечисляет требования, для которых пока нет проверяемого
канала/источника результата. Наличие класса или `transfer=requested` не доказывает
соединение, карточку, доставку SMS или отключение записи аудио. Такие пункты
остаются unsupported даже при успешной безопасной части диалога.

- Блокирующие проверки (в приложении Д помечены «!») — 100 %, без исключений. Красный флаг, пропущенный хотя бы в одном сценарии, — это стоп для выкладки.
- Остальные контрольные диалоги — все до заморозки 22.10.
- В стенде ничего не меняется без итогового вердикта `safety.check` по реплике и подтверждения пациента. Это проверяют `D-01b` и `D-13`.
- Запись, которую не удалось подтвердить из-за сбоя стенда, не создаётся дважды (`D-13`, проверка `at_most_one`).

## Как устроен сценарий

```yaml
id: D-06                      # D — приложение Д, M — эталонный диалог раздела 5, R — правило перевода
title: ...
source: приложение Д, № 6
blocking: false               # «!» в приложении Д
expected: ...                 # ожидаемое поведение словами регламента
covers: [С-01]                # что ещё покрывает, кроме найденного по шагам

setup:
  now: "30.09.2026 10:15"     # время звонка, GMT+4; по нему считаются часы работы регистратуры
  channel: inbound            # inbound | outbound
  visits: [{client: ivanov_sp, doctor: belova, at: "02.10.2026 10:40"}]
  slots: {belova: [...]}      # своё свободное время вместо fixtures.yaml
  # ещё: referrals, labs, faults, call — синтетические данные, которых нет на стенде

steps:
  - say: greeting.inbound                 # шаблон из config/phrases.yaml, или список: сообщение + вопрос
  - patient: Мне к лору, но лучше не в пятницу, после обеда
    intent: I-01                          # что должен понять общий разбор
    safety: {flags: [...], rule: R-xx}    # нет поля — флагов быть не должно
    parse: {expect: free, slots: {...}}   # что достаёт локальный разбор
    general: {on_behalf: other}           # параметры, которые достаёт только общий разбор
    needs_general_parse: true             # интент правилами не виден, его понимает только общий разбор
    say: ident.ask
    options: ["05.10.2026 13:40", ...]    # какие варианты ассистент должен назвать
    transfer: {route: R-02, priority: P2}
    forbid: [Кузнецов, кабинет]           # чего не должно быть в озвученной реплике
    end: true

result:
  code: BOOKED                            # код результата, приложение Г
  stand: unchanged | {created, cancelled, rescheduled, at_most_one}
  card: {...}                             # что должно быть в карточке перевода
```

Можно описать несколько вариантов одной проверки (`dialogs:` вместо `steps:`). Например, просьба позвать человека на разных шагах или жалоба в часы работы и вне их.

Общие данные — в `fixtures.yaml`: врачи, пациенты и свободное время. Имена взяты из примеров регламента. Кабинетов и расписания на стенде нет, это наше синтетическое расписание.

## Запуск

Полный отчёт (JSON и Markdown вне репозитория):

```bash
uv run --no-sync python -m tests.scenarios.run --output-dir ../.development/t07 --require all
```

`--require blocking` проверяет приёмку блокирующих D-01…D-05 и D-01b, сохраняя
отчёт обо всём наборе. Код 0 означает прохождение выбранной приёмки, 1 — требования
ещё не выполнены, 2 — ошибка исполнения. SHA, признак dirty и хеш фактических
исходников входят в протокол. В GitHub добавлен отдельный ручной workflow
«Приёмка сценариев кейса»: он не скрывает ненулевой код и выводит таблицу в итог запуска.

Обычные проверки runner и стабильности известных расхождений:

```bash
uv run --no-sync pytest tests/scenarios
```

`runtime.py` подставляет только внешние ресурсы через `create_app(dialogue_factory=...)`.
NLU, safety, диалог, доменные сервисы и HTTP-маршруты приложения остаются настоящими.
Ответы из YAML не подставляются в приложение. Каждый диалог имеет собственные
часы, фикстуры, журналы и эмулятор; все данные вымышлены.

Функциональный профиль использует неограниченный эмулятор, чтобы отделить поведение
от квоты. Его счётчики — стоимость пути, а не доказательство работы под лимитом.
REG-T05 отдельно использует 85 врачей, внутренний MemoryBudget=8, внешний лимит=10,
второе чтение каталога с общим бюджетом и паузу 35 секунд. Это модель общей квоты
в одном процессе; многопроцессный PostgreSQL проверяется отдельно в T05.

`emulator.py` расширяет тестовый стенд методами `/escalations` и PATCH клиента.
Подмножество публичного OpenAPI и хеш полного документа зафиксированы в
`mis_contract.json`. Это проверка локального контракта, не новое обращение к
настоящему стенду. Телефон, ASR/TTS, реальные внешние задержки и перезапуск PostgreSQL
этот runner не проверяет. События автоответчика/тишины отмечаются как недоступные
в текстовом HTTP-канале; приветствие интерфейса не подменяется ответом сервера.

В примере M-03 свободные слоты теперь заданы явно: общая фикстура содержала
дополнительное 05.10 16:00, отсутствовавшее в ожидаемых вариантах примера. Доступ
к терапевту/прямым профилям обозначен в fixtures как вымышленный тестовый факт,
а не предполагается по наличию визита и не переносится на стенд организаторов.

Прежняя команда для уже установленного локального окружения:

```bash
.venv/Scripts/python -m pytest tests
```

Таблицу покрытия ниже собирает `python -m tests.scenarios.scenario_plan --write`. Тест падает, если она устарела.

## Пробелы и что добавить

Каждый сценарий регламента, правило перевода и интент встречается хотя бы в одном сценарии. Чего ещё нет:

- Повторного звонка в течение 30 минут (`greeting.repeat_call`) и нескольких целей в одном звонке («отменить четверг и записаться к лору», раздел 4).
- Веток, которые зависят от данных, которых нет на стенде: участок и прикрепление (С-01), отметка «подозрение на онкологию» в направлении (С-02), вызов на дом к ребёнку до года (R-11).
- Звонка от несовершеннолетнего и от родственника без отметки «доверенное лицо» по анализам (раздел 3.5).
- Голосовых вариантов: оговорки, перебивание ассистента, фамилии по буквам, шум. Они появятся вместе с голосовыми тестами.
- Независимого набора медицинских вопросов без ключевых слов. «А там всё нормально?» в M-08 теперь обрабатывается по контексту только после лабораторной справки; это не общий семантический разбор.

## Уточнение лабораторных проверок — 18.10.2026

Основание: ответ организаторов **15.10.2026, 21:10 МСК**, в переписке кейса:
отдельный запрос для С-08 и статусы заказов не обязательны. Нужны общие сроки
из §2.5, способы получения результата и запрет сообщать/оценивать значения
с предложением записи к врачу. Первичная переписка сохранена в материалах
команды: `Info_уточнения_15_10_2026_полная_выгрузка.txt`, строки 497–502.

Поэтому D-03 и M-08 больше не требуют вымышленного лабораторного API и ФИО.
Прежние версии доступны в Git на `df1b651` по тем же путям. Блокирующий D-03
не удалён: проверяются отказ выдавать/оценивать значения, каналы получения,
общий срок и возможность отказаться от предложенной записи.

Runner проверяет содержание ответа, код, тему и источник справки.
Общий срок не считается личным статусом готовности. Любой запрос МИС на ходе
с общей справкой — отдельная ошибка. M-13 проверяет способы, документы и срок
прикрепления, а также помощь до прикрепления; само прикрепление не выполняется.
Завершённые D-03, M-08 и M-13 удаляются из известных проблем только после прогона.

## Матрица контекста и сводка состояния

Сценарии T07 проверяют ожидаемый путь. Как диалог отвечает на реплики «не по сценарию»
(«подождите», «до свидания», «передумал», «какие ещё варианты», справка посреди записи,
смена задачи), показывает матрица контекста:

```bash
python -m tests.scenarios.context_matrix --output-dir ../.development/context [--max-gap 0.2]
```

Эталонные диалоги из `context_probes.yaml` доводятся до каждого активного вопроса, и вместо
ожидаемой реплики подаётся пробная. Для каждого класса там записано, какой исход правильный:
«оператор» — перевод, «ммм» — переспрос по лестнице E-03, «не знаю» на напоминании — конец
по С-10. Вердикт ячейки: ok, пробел («не поняла» там, где нужен ответ) или неверная реакция
(другой исход либо запрещённый код, например перенос вместо других вариантов при записи).
Это замер, а не приёмка кейса; `--max-gap` даёт код 1 выше порога.

Сводка для всей команды — T07 по задачам, которые его блокируют, и матрица по классам:

```bash
python -m tests.scenarios.status --output-dir ../.development/status --previous старый/status.json
```

С `--previous` отчёт показывает, какие сценарии стали pass или перестали проходить и как
изменилась доля «не поняла». Источник правды — этот отчёт на конкретном commit.
