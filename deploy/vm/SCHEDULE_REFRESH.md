# Обновление индекса расписания (служба и ручные команды)

Индекс расписания (`SCHEDULE_INDEX_PATH`, обычно `data/schedule.sqlite`) строится из
книги Excel и свежего каталога врачей стенда и действует 24 часа. Обновитель работает
так: получает каталог через общий лимит с приоритетом BACKGROUND, строит кандидата
рядом с рабочим файлом, полностью проверяет его и только потом атомарно публикует.
Приложение замечает новое поколение само (в пределах ~30 секунд) — перезапуск служб
и обрыв звонков не нужны. При любой ошибке рабочее поколение не трогается и живёт
до своего обычного срока; продлевать срок вручную нельзя.

Во всех командах ниже compose вызывается из корня проекта:
`docker compose --env-file .env -f deploy/vm/compose.yaml ...` (дальше — `dc`).

## Запуск и остановка

Книга расписания должна лежать как `data/schedule.xlsx` и быть доступна на чтение.

Обновителю нужны права **записи в каталог data**, чтобы создавать lock/кандидат и
атомарно переименовывать индекс. На ВМ data принадлежит пользователю развёртывания,
поэтому в локальном `.env` Compose задайте `SCHEDULE_UPDATER_UID` и
`SCHEDULE_UPDATER_GID` равными его `id -u` и `id -g`. По умолчанию используется10001,
что подходит только при соответствующем владельце/правах data. Не менять владельца
всего проекта и не открывать каталог всем на запись. Backend/voice продолжают
работать со своим сервисным UID и читают опубликованный индекс0644.

Для `refresh --catalog` принимается каталог не старше5минут по `captured_at`.
Старый JSON не считается новым чтением МИС и не продлевает срок индекса.

- Запуск: `dc up -d schedule-updater`
- Остановка: `dc stop schedule-updater`
- Логи: `dc logs -f schedule-updater`

Служба сама решает, когда пора: попытка делается, когда до конца срока индекса
остаётся меньше 2 часов (один GET /doctors на попытку), после неудачи повтор —
не раньше чем через 15 минут. Если индекс свежий (например, обновлён вручную),
запросов к стенду служба не делает.

## Одно ручное обновление

```sh
dc run --rm schedule-updater python -m app.scheduling.cli refresh \
  --workbook data/schedule.xlsx
```

Команда печатает JSON-статус и завершается с кодом 0 только при успешной проверке
и публикации. Если служба в этот момент уже обновляет индекс, ручной запуск получит
`REFRESH_ALREADY_RUNNING` и ничего не изменит.

## Статус

```sh
dc run --rm schedule-updater python -m app.scheduling.cli refresh-status
# или без запуска контейнера:
cat data/schedule.sqlite.refresh-status.json
```

Поля: `ok`, `finished_at`, `last_success_at`, `generation` (время построения
опубликованного поколения), `expires_at`, хеши книги и каталога, счётчики врачей
и слотов, `error_code`. Секретов и сырых ответов МИС в статусе нет. Отсутствие файла
даёт `NO_STATUS` — обновитель ещё ни разу не завершал цикл.

## Частые ошибки

- `INDEX_SCOPE_MISMATCH` — каталог не от этого режима/адреса/токена стенда. Проверьте
  `.env` (APP_MODE, MIS_BASE_URL, MIS_TOKEN); индекс учебными ID не строится.
- `INVALID_WORKBOOK`, `MISSING_WORKBOOK_SHEET`, `INVALID_PERIOD` — книга повреждена
  или не той формы; замените `data/schedule.xlsx` выданным файлом.
- `DOCTOR_NOT_UNIQUELY_MATCHED` — врач книги не сопоставился однозначно по ФИО
  и специальности со справочником стенда; разбирается вручную, публикаций нет.
- `LOCAL_RATE_LIMIT`, `RATE_LIMIT` — общий бюджет исчерпан за разговорами; служба
  повторит позже сама, лимит не повышать.
- `SCHEDULE_NOT_CURRENT` в ответах поиска — срок индекса истёк, а обновление не
  удалось. Это честный отказ «расписание недоступно», а не «нет слотов»: смотрите
  статус и причину выше, не трогайте даты в файле.

## Права доступа

Приложение в контейнере работает от UID10001. Опубликованный индекс и файл статуса
обновитель и ручной импорт выдают с правами 0644 (чтение всем): секретов и данных
пациентов в них нет, область токена представлена только хешем. Файл каталога врачей
остаётся промежуточным и приложению не нужен. Не делайте рекурсивный chmod на весь
проект; если индекс когда-то создан вручную с 0600, достаточно:
`chmod 644 data/schedule.sqlite`. Каталог `data/` должен быть доступен на проход (x).

## Откат публикации

Отдельной копии прошлого поколения обновитель не хранит: неудачное обновление
рабочий файл не заменяет, поэтому откатывать обычно нечего. Если опубликованное
поколение оказалось нежелательным (например, заменили книгу ошибочной):

1. `dc stop schedule-updater`
2. Верните прежнюю книгу в `data/schedule.xlsx`.
3. Опубликуйте её как новое поколение ручной командой `refresh` (см. выше)
   либо прежним путём `fetch-doctors` + `import-xlsx --replace`.
4. Проверьте `refresh-status` и `check`: процессы приложения перейдут на это
   поколение сами; рестарт `app` не требуется.
5. `dc up -d schedule-updater`

Файлы `*.refresh-candidate.sqlite` и `*.refresh-catalog.json` рядом с индексом —
остатки прерванного цикла; рабочим расписанием они не являются, обновитель уберёт
их сам при следующем запуске.
